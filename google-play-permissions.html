Cette page présente le contexte d’utilisation des permissions sensibles pouvant être demandées par l’application Transfert Données Téléphone, notamment pour les modules de migration SMS et historique d’appels lorsqu’ils sont disponibles.

1. Objectif principal de l’application

Transfert Données Téléphone est une application de migration de données entre deux appareils Android. Son objectif est d’aider l’utilisateur à transférer ses données accessibles depuis un ancien appareil Android vers un nouvel appareil Android.

Les transferts sont conçus pour être effectués localement entre les appareils de l’utilisateur, sans serveur externe de Neova Labs ou de SASU AMINE TELECOM destiné à recevoir les données transférées.

2. Principe de minimisation des permissions

L’application doit demander uniquement les permissions nécessaires au module utilisé par l’utilisateur. Les permissions sensibles ne doivent pas être demandées au démarrage si l’utilisateur n’a pas choisi la fonctionnalité concernée.

Si l’utilisateur refuse une permission, le module concerné doit être ignoré ou limité, sans bloquer les autres catégories de transfert.

3. Permission READ_SMS

Si le module SMS est disponible et activé, la permission READ_SMS peut être demandée sur l’ancien appareil afin de lire les SMS existants et de les préparer pour le transfert vers le nouvel appareil.

  • Utilisation : lecture des SMS existants pour migration ;
  • Déclenchement : uniquement après action explicite de l’utilisateur ;
  • Destination : transfert local chiffré vers le nouvel appareil ;
  • Publicité : le contenu des SMS n’est pas utilisé pour la publicité ;
  • Serveur externe : les SMS ne sont pas envoyés vers un serveur de Neova Labs / SASU AMINE TELECOM.

4. Restauration des SMS

Pour restaurer des SMS sur le nouvel appareil, Android peut exiger que l’application devienne temporairement l’application SMS par défaut.

Dans ce cas, l’utilisateur doit recevoir une explication claire avant toute demande de changement d’application SMS par défaut. Après la restauration, l’application doit guider l’utilisateur pour remettre son application SMS habituelle.

La permission WRITE_SMS ne doit pas être ajoutée sans justification technique actuelle. L’écriture des SMS restaurés dépend principalement du rôle d’application SMS par défaut exigé par Android.

5. MMS

Les MMS sont plus complexes que les SMS, car ils peuvent contenir des pièces jointes, des données opérateur, des formats spécifiques et des éléments dépendants de l’appareil ou de l’opérateur.

Si le transfert MMS n’est pas pris en charge dans une version de l’application, cela doit être indiqué clairement à l’utilisateur dans l’application et dans les informations de publication.

6. Permission READ_CALL_LOG

Si le module d’historique d’appels est disponible et activé, la permission READ_CALL_LOG peut être demandée afin de lire l’historique d’appels de l’ancien appareil pour le transférer vers le nouvel appareil.

  • Utilisation : lecture de l’historique d’appels pour migration ;
  • Données concernées : numéro, date, durée, type d’appel et informations disponibles selon Android ;
  • Déclenchement : uniquement après action explicite de l’utilisateur ;
  • Publicité : l’historique d’appels n’est pas utilisé pour cibler les publicités ;
  • Serveur externe : l’historique d’appels n’est pas envoyé vers un serveur de Neova Labs / SASU AMINE TELECOM.

7. Restauration native du journal d’appels

La restauration native du journal d’appels dans l’application Téléphone Android peut être limitée par les règles Android et Google Play.

Selon les restrictions applicables, l’application peut choisir d’afficher l’historique d’appels transféré dans une section locale de l’application plutôt que de l’insérer dans l’application Téléphone native.

Si une restauration native nécessite que l’application devienne temporairement l’application Téléphone par défaut, l’utilisateur doit être informé clairement avant toute demande. L’application ne doit pas passer d’appel automatiquement ni intercepter volontairement les communications de l’utilisateur.

8. Données sensibles et publicités

Les données sensibles traitées pour la migration, comme les SMS, le journal d’appels, les contacts ou les calendriers, ne doivent pas être transmises à Google AdMob par le code de l’application.

Les publicités peuvent utiliser des données publicitaires techniques selon les règles Google et le consentement de l’utilisateur, mais les données transférées ne doivent pas être utilisées pour cibler les publicités.

9. Écrans sans publicité

Aucune publicité ne doit être affichée pendant les étapes sensibles liées aux permissions ou au transfert.

  • Écrans de demande de permissions ;
  • Écrans liés aux SMS ;
  • Écrans liés au journal d’appels ;
  • Écrans de changement temporaire d’application SMS ou Téléphone par défaut ;
  • Scan ou génération QR ;
  • Connexion entre appareils ;
  • Transfert en cours ;
  • Restauration de données ;
  • Rapports contenant des informations sensibles détaillées.

10. Consentement utilisateur

Avant toute permission sensible, l’application doit expliquer :

  • pourquoi la permission est nécessaire ;
  • quelle donnée est lue ou restaurée ;
  • que le transfert reste local entre les appareils ;
  • que les données ne sont pas utilisées pour la publicité ;
  • que l’utilisateur peut refuser et continuer sans le module concerné.

11. Déclaration Play Console

Si les permissions SMS ou journal d’appels sont présentes dans le manifeste de l’application, elles doivent être déclarées dans Google Play Console selon les règles applicables.

Le cas d’usage à présenter est la migration de données entre appareils appartenant à l’utilisateur. La déclaration doit expliquer que les données sont utilisées uniquement pour le transfert demandé par l’utilisateur.

12. Plan de retrait si nécessaire

Si une permission sensible n’est pas acceptée par Google Play ou si un module ne peut pas être justifié, le module concerné doit pouvoir être désactivé sans casser le reste de l’application.

  • Module SMS désactivable indépendamment ;
  • Module journal d’appels désactivable indépendamment ;
  • Suppression des permissions correspondantes dans le manifeste si nécessaire ;
  • Maintien des autres modules : contacts, médias, fichiers, audio, calendrier et transfert local.
